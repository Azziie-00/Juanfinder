## Resulting workflow

Pending applications appear in the adviser's bell, with group, course, unique member count, original submission time, 24-hour deadline, actual application attachment summary, status, View and Accept. Groups contains accepted assignments only. Dashboard retains its counts and announcement/calendar. View opens the same application for both read and unread notifications immediately, without waiting for its read receipt; a failed read-status write does not block View or falsely mark it read. Reject remains available inside application details and sends no applicant notification.

Acceptance reuses the existing database transaction: group, application, adviser and member locks protect ownership, finalized status, course, capacity, member assignments and the exact deadline. One accepted group consumes one slot. Repeated or competing requests cannot double-assign it. Terminal events stay in history; Accept is disabled. Submission, acceptance and expiration notifications are database events with unique event keys, rather than frontend placeholders.

Only the session-authenticated API accesses notification RPCs; recipient IDs come from the verified session. Direct anon/authenticated Supabase roles cannot read the table or execute these service RPCs. Application metadata and private signed file URLs are scoped to the selected adviser and application. Application attachments use group_adviser_application_documents and application-requirements paths in the private student-portfolios bucket; they are separate from student portfolio records.

A successful lookup returning zero files displays the no-files message. Failed metadata lookup does not establish zero files. If the upload transaction commits but its follow-up metadata read fails, the submission still succeeds and omits unconfirmed metadata; a later View retrieves committed attachments. Do not resubmit a committed application to retry this lookup. Bell refresh failures preserve loaded notifications and emit only sanitized operation/status diagnostics. An expiry-maintenance failure does not hide existing inbox events. The overlays contain no load-error or Retry controls. Polls and focus events reuse an in-flight inbox request rather than cancelling it every five seconds; a 20-second timeout releases a stalled request for the next refresh. The API-confirmed acceptance/rejection status is retained immediately even if the next inbox refresh fails, so ACCEPT cannot reappear for that decision. Each attachment also has a direct Download action that does not depend on successful preview extraction.

## Expiration scheduler

011 attempts to install pg_cron and schedule an every-minute job. Verify in Supabase SQL Editor:

```sql
SELECT extname FROM pg_extension WHERE extname = 'pg_cron';
-- Run the following only if pg_cron is installed:
SELECT jobid, jobname, schedule, command, active FROM cron.job
WHERE jobname = 'juan-finder-expire-adviser-applications';
SELECT status, return_message, start_time FROM cron.job_run_details
WHERE jobid IN (SELECT jobid FROM cron.job
  WHERE jobname = 'juan-finder-expire-adviser-applications')
ORDER BY start_time DESC LIMIT 5;
```

If the extension/job is unavailable, configure an always-running hosting scheduler or Windows Task Scheduler every minute to run `node /absolute/path/to/Juanfinder/server/expire-adviser-applications.js`. Configure SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY in server/.env or its environment. Keep the service key server-side. Browser polling catches overdue applications when a user returns, but does not replace an unattended scheduler. Database acceptance still checks the exact deadline even between scheduled runs or after waiting for locks.

No new database, table, dependency or data reset is needed. The existing temporary-password workflow is preserved.

### Persistent website activity

Apply **`server/migrations/015_website_activity.sql`** in Supabase SQL Editor after existing migrations to enable persistent activity history. No new dependency is required. This additive migration adds nullable activity columns to `users` and `auth_sessions`, plus a session-insert trigger and a service-role-only recording function. It does not reset data, invent old timestamps, or overwrite history when rerun. It has been tested on isolated databases; it has not been applied to the live database from this workspace. Without 015, authentication falls back to the original session columns, the profile reports that activity tracking is unavailable, and `/api/activity` returns HTTP 202 with `trackingAvailable: false`. The browser stops attempting activity writes for that page. Other features and logout continue working; missing activity infrastructure is never presented as recorded history.

At successful login, the database locks the account, snapshots its last recorded activity into the new session's `previous_activity_at`, and starts the current session with a database-generated timestamp. The snapshot stays fixed for that session, including profile refreshes, activity updates and other concurrent logins. `GET /api/profile` returns only the signed-in session's snapshot as `PreviousActivityAt` with `Cache-Control: no-store`. User IDs and timestamps supplied by the browser are not accepted as activity data. Anonymous/authenticated Supabase roles cannot execute the recording function or read the private tables.

The shared layout posts to authenticated `POST /api/activity` for foreground visits, pointer/keyboard/scroll activity and visibility changes. Requests are coalesced to at most once per minute during normal interaction; pending activity is flushed on leaving a page, hiding/closing the tab, or navigating. Logout records a final server timestamp before deleting the session. Notification polling does not count as activity, and idle/background tabs do not send periodic heartbeats. Best-effort unload requests can be lost during an abrupt browser/device shutdown; the last successfully recorded activity is retained.

The user-level timestamp survives logout and expired-session cleanup. The next login captures it as the previous session's latest activity. My Profile's Miscellaneous section shows **Last active** using the browser's local timezone, or **No previous activity recorded.** when history is absent. Sessions that already existed when this migration ran keep a NULL snapshot until the next login; historical activity cannot be reconstructed reliably. Tests cover both roles' actual login/logout endpoints, immutable snapshots, concurrent sessions, expired sessions, spoofed IDs/timestamps, migration reruns and database permissions, plus desktop/mobile menu access and local-time rendering.

`GET /api/adviser/dashboard?search=...` derives the adviser ID exclusively from the bearer session and requires a real Adviser account. The report function is executable only by the server's service role. It collects groups through `groups.adviser_id`, counts distinct Student users (including legacy owners missing a membership row), and calculates remaining slots as `greatest(0, adviser_capacity - assigned_groups)`. Summary counts remain scoped totals when search changes. Search is a literal, case-insensitive substring of student name or student ID, not a SQL wildcard expression. It paginates each query using the actual returned row count, so server page caps below the requested size do not truncate results.
